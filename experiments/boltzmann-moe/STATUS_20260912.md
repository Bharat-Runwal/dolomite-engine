## WATCHDOG GOTCHA — read before touching jobs

The watchdog identifies tracked jobs by **job ID recorded in
`scripts/watchdog/watchdog_state.txt`**, not by name in `bjobs`
(`watchdog_loop.sh`, the `last_jid=$(grep "^$name " "$STATE" ...)` block). So:

- A job you submit **by hand** is invisible to it. On its next poll it decides the
  job is "not alive" and submits a **duplicate**. This happened here: all 8 wave
  jobs got a second PEND copy within minutes, which would have double-booked the
  32-GPU quota.
- Fix applied: seed the state file with one `<name> <jobid> 0` line per running job.
  State file format is exactly `name jid count`, space-separated.
- To pause a run you must do BOTH: comment its conf line (`#PAUSED `) **and**
  `bkill` it. Killing alone just makes the watchdog resurrect it.
- After any manual submission, re-seed the state:

      bjobs -noheader -o "jobid job_name stat" | grep iclr_ | \
        while read jid name st; do echo "$name $jid 0"; done > \
        experiments/boltzmann-moe/scripts/watchdog/watchdog_state.txt

### Caveat that must not be lost

These arms use `I_e` = 512-1024, while the h1 reference arms use `I_e` = 2048. They
are iso-*parameter* but **not iso-expert-width**, so the ~2pp gap to the h1 numbers
(48.32 dense) is confounded by expert width — consistent with this project's own
earlier finding that narrow experts underperform. Raising K at fixed parameter budget
buys FLOPs but narrows experts; that trade is inside this table, not across it. The
table footer now says so, and the h1 reference values printed there are avg10-restated
rather than the avg9 figures still in PROGRESS.md.

### 1. THE HEADLINE — energy routing matches a learned router at matched k/K

Same expert form (w1w2), same K, same k, same backbone, same tokens, same eval code:

    energy router   45.69 avg10 / 40.00 ppl
    LEARNED router  45.66 avg10 / 40.13 ppl      <- standard MoE baseline
    difference      +0.03pp / -0.13 ppl

That is **parity**, and it is the fair comparison the paper needs: no learned gate, no
load-balance loss, +0.03pp. The hopfield form at the same k/K is +0.23pp over the
learned router. Neither margin is a win; both support "energy routing costs nothing in
quality", which is exactly the framing the appendix now uses.

### 2. More experts at fixed k is BETTER and CHEAPER

At fixed k=2, going K=16 -> K=32 improves accuracy **and** halves cost:
`hop_K16_top2` 45.89 @ k/K=0.125 -> `hop_K32_top2` **46.26 @ k/K=0.062**. That is
+0.37pp for 2x fewer FLOPs. And top-1 of 32 (k/K=0.031, a **32x** arithmetic
reduction) still scores 46.15, only -0.43pp below dense.

So the frontier is non-monotone in k/K but improves with K at fixed k. Correct framing:
**quality is flat to within ~0.4pp from k/K = 1.0 down to 0.031**, and the cheapest
points are not the worst. This supersedes my earlier "-0.69pp for 8x" read, which
looked at the wrong axis (k/K rather than K).

### 3. The pure single-block architecture FAILS — clear negative result

`pure_hop_K16_top2_1blk` (no GPT prefix, all params in one block applied 8x):
**42.94 avg10 and 69.66 ppl** against ~40 ppl for every hybrid. Not a near miss.
This matters because that was the architecture where the FFN speedup would have been
**end-to-end** rather than capped near 22%. So the end-to-end claim is not available

## 2026-09-13 ~04:30 UTC — two infrastructure failures found and fixed

Both discovered by the health check, both fixed in-config. Recorded because they will
recur for anyone extending this grid.

**1. A real Switch MoE cannot run under `torch_compile: true` here.**
`iclr_switch_K16_top2` died with an NCCL collective timeout (rank desync at work 16/17);
`iclr_switch_K16_top2_shared` died with a torch-inductor error and a 1800 s gloo send
timeout. Cause: the `MoE` class routes with **data-dependent shapes** (tokens per expert
vary each step), so under `torch_compile` + FSDP it recompiles and the ranks fall out of
step. Fix: `torch_compile: false` for those two arms only. Our energy-MoE classes are
unaffected because they compute every expert on every token, so their shapes are static
— which is itself a note worth keeping: the dense-compute implementation that costs us
FLOPs is also what makes us compile-friendly.

**2. The ~400M tier OOM'd on 80 GB.** All three arms: "tried to allocate 3.06 GiB, 1.9
GiB free". At d=1024 with `I_e=17920`, per-expert activations at
`micro_batch_size=4` x 4096 tokens do not fit. Fix: `mbs 4 -> 1`, `ga 4 -> 16` (holds
tokens-per-step identical) plus block gradient checkpointing. Resubmitted.

**Watchdog duplicated `pure_hop_isoP` a third time.** The race is structural: it polls
every 5 min and any hand-submitted job is invisible until the state file is seeded, so
seeding must happen *after* every submission batch, not before. Killed the duplicate.
