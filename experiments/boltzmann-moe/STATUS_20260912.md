## WATCHDOG GOTCHA — read before touching jobs

The watchdog identifies tracked jobs by **job ID recorded in
`scripts/watchdog/watchdog_state.txt`**, not by name in `bjobs`
(`watchdog_loop.sh`, the `last_jid=$(grep "^$name " "$STATE" ...)` block). So:

- A job you submit **by hand** is invisible to it. On its next poll it decides the
  job is "not alive" and submits a **duplicate**. This happened here: all 8 wave
  jobs got a second PEND copy within minutes, which would have double-booked the
  32-GPU quota.
- Fix applied: seed the state file with one `<name> <jobid> 0` line per running job.
  State file format is exactly `name jid count`, space-separated.
- To pause a run you must do BOTH: comment its conf line (`#PAUSED `) **and**
  `bkill` it. Killing alone just makes the watchdog resurrect it.
- After any manual submission, re-seed the state:

      bjobs -noheader -o "jobid job_name stat" | grep iclr_ | \
        while read jid name st; do echo "$name $jid 0"; done > \
        experiments/boltzmann-moe/scripts/watchdog/watchdog_state.txt

### CORRECTION to the "~06:00 UTC" entry above

That entry says 8 GPUs is not available on demand here. **That was wrong, and the

from the one that killed these runs.**

sparse-routing study with one dense reference point, not the other way round.

**Sparse computation: no, and we must not claim it.** No arm converts routing
sparsity into a training-time saving:

| class | what it does | sparse compute? |
|---|---|---|
| `EnergyFF_BoltzmannMoE` | evaluates all K experts, then `p = p * mask` (`energy_ff.py:548`) | no |
| `TopK_Energy_MoE_MLP` | docstring is explicit: "All n_experts compute their gradients in the forward pass; only top_k outputs are used" | no |
| Switch-style `MoE` | *has* a grouped-dispatch path, but `scattermoe` is not enabled in our configs | no (fallback) |

That is why dolomite logs active params == total params for every arm. It is a
property of the implementation, not the method: rejected experts are multiplied by
**exactly zero**, so the trained function is precisely a top-$k$ model and a sparse
inference kernel reproduces it up to fp associativity. **The FLOP claim is therefore
inference-only** (the measured 19×), and the appendix now says so explicitly
(`app:dense-vs-sparse`).

### A real caveat on the parity result, found while checking the above

The energy arms mask **without renormalising** → `sum(p) ≈ 0.4525` at K=16, k=2.
Both baselines normalise to exactly 1 (the learned router softmaxes over the top-$k$
logits; the Switch arms set `normalized_topk`). So the energy block's output is ~2×
smaller in magnitude than the baselines'. `scale_ff` can absorb this and both families
trained under their own convention, so **neither is handicapped and parity is not
invalid** — but it is not an identical comparison, and it was nowhere in the paper.
Now in the appendix, and `renormalize_topk` exists as a config flag
(**default `false`**, so no existing config or checkpoint changes behaviour).

### Same checkpoint, ~08:15 UTC — `iclr_big_learn_pure` died in inductor; fixed

jid 1589109 EXITed after ~30 min, all 8 ranks raising the same error. Traced to the
exact pass rather than guessed:

```
post_grad_passes -> spmd_check(gm) -> dist.all_gather_object(all_hashes, structure_hash, pg)
InductorError: RuntimeError: [gloo/transport/tcp/unbound_buffer.cc:129]
                Timed out waiting 1800000ms for send operation
```

`spmd_check` is a **diagnostic** pass that all-gathers a graph-structure hash so it can
warn about non-SPMD graphs. It requires every rank to reach the same compile point
together; across 2 nodes they did not, so the gloo all_gather blocked for its full
1800 s. The pass is gated on `reorder_for_compute_comm_overlap`, which dolomite sets
unconditionally at `lm_engine/distributed.py:57`, so it is always on for us.

**This is the same failure already fixed on both Switch arms**, and for the same
reason: a learned router makes per-expert work data-dependent, which triggers
rank-dependent recompiles. Fix applied identically — `torch_compile: false` on this arm
only. `iclr_big_hop_pure` compiles fine and keeps `torch_compile: true`; its routing is
a dense masked mixture with static shapes.

**Fairness:** compile changes kernel fusion, not the function or the optimisation
trajectory, so the hop-vs-learn comparison stays valid; only wall-clock differs.
Empirically compile-off is not a penalty at this scale — `iclr_switch_K16_top2` runs
compile-off at **0.46 s/step** while the compiled 4-GPU arms sit at 0.78-1.04 s/step.

A narrower fix exists and is recorded in the config but deliberately **not** used:
`torch._inductor.config.aten_distributed_optimizations.spmd_check = False` drops only
the diagnostic collective (its mismatch action defaults to `"warn"`, so it prevents
nothing). Rejected because if the graphs really are non-SPMD it would move the hang to
a real NCCL collective later, which is a worse failure to debug.

**Caught a methodology error before reporting it.** My first probe applied a raw `-E/τ` while

probe replicates `_logits` exactly. The finding survived, but the numbers moved a lot
(hybrids 10.8 → 4.20), so the first table would have been wrong. Gaussian probes measure
*intrinsic* selectivity, so a bad number is conclusive and a good number is only necessary.

### Repulsion is the wrong lever, and this is the interesting part

Repulsion penalises expert-**weight** cosine similarity and **it works**: `cos_mean ≤ 0.021`,
`cos_max ≤ 0.067`, **zero dead experts**, norm ratios 0.49–0.97 on every single arm. The
experts stay genuinely distinct — and one of them wins anyway. **Weight diversity does not
imply routing diversity.** The missing mechanism has to act in routing space.

### What was implemented

1. **In-graph load tracking** — buffers accumulated with pure tensor ops, no `.item()`, so
   they trace under `torch.compile`. Verified: `tokens=2048` and `eff_n` reported from a
   compiled forward, which the old path could never do. Exposed as
   `load_effective_n_experts`, `load_max_share`, `load_min_share`,
   `load_mean_token_entropy` via `pop_load_metrics()`, read by the trainer each step.
2. **Aux-loss-free balancing** (`balance_rate`, DeepSeek-V3 style) — a per-expert additive
   logit bias nudged under `no_grad` toward under-loaded experts. **Not a loss, no gate
   params**, so the paper's "no load-balancing loss and no gate parameters" claim survives.
   Verified functional in isolation: forcing `bias[0]=+5` moves eff_n 7.76 → 1.005.
3. **`balance_rate` defaults to 0.0 and the OFF path is byte-identical** to the unmodified
   module (`max|delta| = 0.00e+00`), so every running and resuming arm is unaffected. This
   matters because the watchdog resumes arms into whatever code is on disk.

Bug I introduced and caught in testing: the `pop_load_metrics` insertion landed between
`FusedMoEContainer.forward`'s last statement and its `return out`, so forward returned
`None`. Fixed and verified.

### Why this matters for the paper

The single-block deficit was attributed to architecture (0.32 nats, 7.5× the router
effect). But the energy single-block arm was **also routing to one expert**, i.e. running as
a ~1-expert model while its learned-router counterpart had a working load-balance loss — and
it still lost only 0.06 nats to it. `configs/iclr_balance/pure_hop_isoP_bal.yml` (queued,
preemptable) tests whether balancing restores eff_n toward 4.6 and recovers part of the
deficit. **If it does, the architecture conclusion in `app:attribution` needs revising.**
Left as \CC in the appendix rather than changed on speculation.
